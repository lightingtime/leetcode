我的解法

思路：单遍哈希表。一边遍历数组，一边把「数字 → 下标」存入 HashMap； 对每个元素检查 target - nums[i] 是否已经出现过——出现过就直接返回两个下标，否则把当前数字记进表里继续走。

时间 O(n) 空间 O(n) 边查边存，天然处理重复值

src/LC0001_TwoSum.java提交区
public int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> map = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        if (map.containsKey(target - nums[i])) {
            return new int[]{map.get(target - nums[i]), i};
        } else {
            map.put(nums[i], i);
        }
    }
    return null;
}

最后的 return null 在题目保证有且仅有一个解的前提下不会被执行，作为兜底保留。

思路正确 · 但代码层面有一个可微调点

当前写法对同一个 key 做了两次哈希查找：先 containsKey 判断是否存在，再 get 取值。 可以合并成一次查找——先 get，再判断是否为 null。复杂度不变（均摊 O(1)），只是更紧凑。

当前写法（两次查找）
twoSum 内containsKey + get
if (map.containsKey(target - nums[i])) {
    return new int[]{map.get(target - nums[i]), i};
}
更紧凑（一次查找）
twoSum 内get + null 判断
Integer j = map.get(target - nums[i]);
if (j != null) {
    return new int[]{j, i};
}

改成 return null 绕过了编译，但没有实现任何查找逻辑：

算法判定：单遍哈希表，已是最优

  • 时间复杂度 O(n)：必须遍历每个元素，O(n) 是本题下限；哈希查找把内层比较从 O(n) 降到 O(1)。
  • 空间复杂度 O(n)：用一张哈希表换时间，是空间换时间的标准形态。
  • 正确性：边查边存，重复值场景（如 [3, 3]、target 6）也能正确返回 [0, 1]。
  • 结论：与题目标准解法一致，无需再优化。

代码层面微优化（复杂度已达最优，仅风格）

算法本身已是 O(n) 最优；代码层面 containsKey + get 是两次哈希查找， 可合并为一次 get + null 判断。对比见上方「我的解法」的优化点。
