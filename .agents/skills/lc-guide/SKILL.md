# LC Guide — 解题思路引导

## 定位

- 用户处于「理解概念 / 不知道怎么写 / 写到一半卡住」阶段，还没有稳定的失败用例；若已经跑测试报错/失败，走 lc-analyze。
- 默认不给完整答案；只有用户明确说「给我当前思路的正确答案」才给。

## 上下文纪律（省 token，必守）

- 需要题目/一刷信息时用 `node ".agents/skills/lc-practice/scripts/update_state.js" show --seq <seq>`（约 0.5KB），不要读 `analysis.json`/`progress.json` 原文；要某写法代码时才加 `--code latest`。
- `references/*.md`（dp-subtypes、stack-index-semantics、example-lc4）都按需读对应小节，禁止整篇读；`lc-analyze/references/patterns.md` 是 68KB，只用 `rg -n` 查关键词定位。
- 读用户代码用 `sed -n 'a,bp'` / `rg -n` 取片段，不要整篇 cat；引用行号必须与文件真实行号一致（用 `rg -n` 或 `sed -n` 的带行号输出核对）。

## 流程（严格按序，用户没跟上就停）

0. **先识别子类型（DP 题必做）**：题目分类是「动态规划」时，先判断子类型（线性/区间/树形/背包/状态机/数位/状压），对照 `lc-practice/references/dp-subtypes.md` 决定引导方向；区间 DP 从「正着做会破坏相邻关系」讲起，树形 DP 从「自底向上汇总子节点」讲起，不要只笼统说「这是 DP」。
1. **名词先行**：每个术语先用具体小例子讲清楚（如「下标 vs 第 k 小」「指针/有效起点」「候选」「排除数量」「区间 DP 的最后一步」），一次一个概念，用户确认懂了再继续。公式必须配数字例子（表格/图示），禁止只给公式不给语义。
2. **变量规划**：引导写代码前，先列出「这个解法需要定义哪些变量、每个变量存什么、后续在哪一步用」。用户对变量来源有疑问时，先讲清「从 0 开始、排除后前移」这类语义，再进入下一步。
   - **指针/边界题必给不变量（必做）**：涉及双指针/多指针/下标边界的题，变量含义必须用「区间划分」表述，如「lt 是下一个 0 应放的位置（0 区右边界，不含）；gt 是下一个 2 应放的位置（2 区左边界，不含，gt 位置本身未处理）」，并讲清循环边界为什么这样写（如未处理区是 `[i, gt]` 闭区间，`i == gt` 时还剩最后一个元素必须处理）。先请用户把这段不变量注释写进提交代码，防止凭感觉写条件；用户没写也不卡流程——归档时由 Codex 补齐（约定见 lc-submit 的「讨论中形成的关键注释」）。
   - **变量注释只写精确定义（必做）**：代码注释收敛为一行「区间不变量」定义（如 `lt: [0,lt) 全 0；i: [lt,i) 全 1；(gt,n-1] 全 2；[i,gt] 未处理 → 条件 i<=gt`），禁止堆一大段解释、逐行分支注释；宁可改更自解释的变量名，也不要长注释。
   - **参数定义 + 循环进入条件注释（必做）**：涉及指针/边界/循环的题，注释除变量不变量外还要写清 ① 每个方法参数的精确含义与返回值语义（如「参数 head：待排序链表头」「getMid 返回左半最后一个节点」）；② 循环进入/继续条件的理由（如「fast.next.next != null：保证 slow 前进 ⇔ fast 走满 2 步，两元素时 slow 停在左半最后一个」）。同样一行一条、不堆废话。
   - **注释只针对易错/曾错点（必做）**：注释只加在「容易写错或这次真写错」的地方（循环条件、断链、分治结构等），正确直白的代码不注释；禁止行尾注释（尾注释难读），一律独立行；变量/参数缩写到注释说不清时改名让代码自解释，而不是硬凑注释。
   - **DP 状态说明（DP 题必讲 5 件事，禁止只给公式）**：① `dp` 下标含义（如 `dp[i][j]` 的 `i`、`j` 各代表什么）；② 下标取值范围、端点**含不含**（开区间还是闭区间，如 312 的 `(i,j)` 端点不戳）；③ `dp` 值存什么（最大值/计数/布尔/状态）；④ 转移来源（从哪些已算好的状态来）；⑤ 答案取哪个格子（如 `dp[0][n+1]`，不是 `dp[n-1]`，并说明为什么）。讲完必须让用户用自己的话复述 `dp` 语义再继续。
3. **分块推进**：把解法切成可消化的块（如 出口检查 → 取候选 → 比较排除 → 循环/递归包装），一次只讲一块；每块讲完让用户先写出来再确认，不提前讲下一块。
4. **检查片段**：用户贴代码时逐行对照其变量/分支检查，指出具体变量、行、公式错在哪并解释为什么（引用具体用例或数字），不代写修复。用户反复追问同一概念时换更小的例子重新讲，不默认用户已经懂了。
   - **行号必须与真实代码对应**：引用文件行号前先用 `cat -n <文件>`（或 IDEA 编辑器行号）核对，行号必须与用户文件当前真实行号一致；禁止用 sed/截取片段后的相对行号冒充真实行号，否则用户无法定位到所指代码。
5. **收尾**：所有块完成后让用户跑本地测试；失败转 lc-analyze，通过转 lc-submit。

- 行号引用（lc-guide / lc-analyze 通用红线）：给行号前必须核对（`rg -n '<关键片段>' <文件>` 或 `sed -n 'a,bp'`），与文件真实行号一致；行号错位时先纠正再继续讨论，核对时不要把整个文件贴进对话。

## 引导顺序（用户明确要求）

- **先从最朴素/直观的思想讲起**（如暴力枚举、每根柱子向左右扫描找更矮的），用小例子让用户理解「正确但慢」的做法；
- 确认用户理解朴素思路后，再引入最优解（如单调栈、双指针、DP 优化），并对比两者复杂度（如 O(n²) → O(n)）；
- 不要一上来直接讲最优解；用户卡在「朴素 → 最优」的转化时，再引导「朴素做法慢在哪、哪些重复计算可以用什么结构消除」。

## 高频易混名词（先讲这些）

- **下标 vs 排名/第 k 小**：下标从 0 数、排名从 1 数；下标 i 对应第 i+1 小；「第 k 个」的下标 = 起点 + k − 1。
- **指针/有效起点**：不删数组，用指针标记「从哪开始还算数」，指针只会向右移动。
- **候选下标与封顶**：候选 = 有效部分里第 k/2 个元素；下标 = 起点 + k/2 − 1，数组不够长时取最后一个（`min(len-1, ...)`）。
- **排除数量**：从旧起点到候选下标（含候选）的元素个数 = 候选下标 − 旧起点 + 1；k 减的是实际排除数量，不是理论 k/2。
- **迭代 vs 递归包装**：同一逻辑，迭代用局部变量 + while(true)，递归用参数传递，两者等价。
- **栈存下标时的语义**：下标本身只是位置，必须说明“它代表哪个尚未处理/尚未匹配的位置”；分别解释栈底边界、栈顶最近待处理位置、弹出后新栈顶为何能作为基准，并配 2～5 个元素的逐轮栈状态。模板见 `references/stack-index-semantics.md`。

## 复习模式（二刷，lc-review 联动）

- 复习轮引导标准更高：该题一刷已做过，先让用户**回忆一刷思路**（读 `analysis.json` 的 `approach`/`submissions` 作为对照），回忆不上来再分块引导。
- 名词/变量讲解时，优先以「一刷你用的 XX 写法」为参照对比，指出这次哪里和上次不同；不直接给一刷答案。

## 红线

- 一次只推进一块；用户没确认懂，不进入下一块。
- 不直接给完整答案、不替用户写修复，除非用户明确要「当前思路的正确答案」。
- 解释必须贴用户实际代码结构（变量名、分支、行），禁止用假想的通用写法替代。
- 用户说「没懂」时回退到更小的例子重新讲，不重复同一段话。
- 用户明确说「你来改 / 你帮我改」时：改完**先展示改动代码片段**并说明改动点，等待用户确认与讨论；**未经用户确认，不得直接进入提交流程**（用户后续明确说「提交」才算授权）。

参考实例：`references/example-lc4.md`（名词表 → 变量规划 → 分块清单 → 踩坑案例）；栈存下标时的解释模板见 `references/stack-index-semantics.md`。
